go down for about one second and then back up.

--------------------------------------------------------------------------------

The maximum number of pending transmit frames was limited to the number of ports tested, i.e. 2, regardless of if the
transmit needed to be rate limited to protect loss in the switch under test.

a. When rate limited, as before the maximum number of pending transmit frames is the number of tested ports.
a. When not rate limited the maximum number of pending transmit frames is increased to 48 (NUM_DEFINED_PORTS)

5. Allow operation with different MRMAC ports used for transmit and receive
---------------------------------------------------------------------------

The mrmac_switch_test command line options were changed to allow different MRMAC ports to be specified for transmit and receive.
This is to test MRMAC ports in "simplex" mode.

6. Correct size of transmit frames
----------------------------------

For the above tests, when tried to generate 5000 Mbps per port bandwidth only got about 4937 Mbps.

Realised that the way open_mrmac_device() configured the XDMA transmit fixed size buffers:
a. The actual size of each transmit frame was sizeof (ethercat_frame_t) aligned to a multiple a cache line.
b. Which meant while TEST_PACKET_TOTAL_OCTETS assumed each frame had 1518 bytes were actually transmitted with 1536 bytes.

7. Test different packets sizes and software FCS implementations
----------------------------------------------------------------

For this the VD100_10G_ether_dual design was connected to a T1700G-28TQ switch:
a. VD100 port 0 connected to switch port 27 via 10G DAC cable.
b. 10G DAC cable between switch ports 25 and 26.
c. Switch port VLAN configuration:
   - Port 25 untagged member of VLAN 1025
   - Port 26 untagged member of VLAN 1026
   - Ports 27 and 28 tagged members of VLAN 1025-1026

Attempted to use the full duplex 10G bandwidth on the MRMAC port connected to the switch, by requesting 5000M on each of the
two switch ports under test.

This running on:
a. CPU 12th Gen Intel(R) Core(TM) i3-12100 
b. CPU has avx2 instructions, debugging shows /opt/intel/oneapi/ipp/2026.1/lib/libippdcl9.so.12.1 loaded.
   From https://www.intel.com/content/www/us/en/developer/articles/technical/understanding-cpu-optimized-code-used-in-intel-ipp.html
   the l9 means "Optimized for processors with Intel® Advanced Vector Extensions 2 (Intel AVX2)"
c. AlmaLinux 10.2, with Kernel 6.12.0-211.74.1.el10_2.x86_64
d. Single DDR5 16GB 4400 MT/s 64-bit DIMM

Summary is:
a. No failures during the test.
b. The C implementation of the FCS calculation slowed down the data rate, whereas the ZLIB and IPP implementations still allowed
   the full 10G bandwidth to be achieved.
